# Tabeeby Healthcare OS — Work Plan

هذه القائمة تضبط العمل على إصدار صحي آمن قابل للاختبار، ولا تعتبر ادعاءات الوصف تنفيذًا سريريًا أو تشغيلًا فعليًا.

| الحالة | المجال | العمل |
|---|---|---|
| [ ] | Contract review | مطابقة كل خدمة مع عقود API وطلبات/استجابات Pydantic واضحة والتحقق من المدخلات |
| [x] | Authentication | مراجعة المصادقة، RBAC، الجلسات، الأسرار، ومنع بيانات الاعتماد الافتراضية |
| [ ] | Persistence | استبدال الحالة داخل الذاكرة بحدود تخزين واضحة حيث يلزم، مع migrations وعمليات idempotency |
| [x] | Safety gates | منع أي تشغيل طبي أو تحكم في أجهزة أو إرسال طوارئ حقيقي؛ توفير simulation-only وapproval gates |
| [ ] | Integrations | عزل FHIR/RAG/IoT/notifications والروبوتات خلف adapters قابلة للتكوين مع kill switch |
| [x] | Frontend | مراجعة قابلية البناء، المسارات، حالات الخطأ، وإظهار simulation/disabled states بوضوح |
| [x] | Infrastructure | تصحيح Compose/Kubernetes/Terraform، إزالة كلمات المرور الافتراضية، وتحسين health/readiness |
| [x] | Testing | إضافة اختبارات للمدخلات غير الصحيحة، الصلاحيات، التكرار، approval gate، وعدم التنفيذ الخارجي |
| [ ] | Security | فحص الأسرار، التبعيات، إعدادات الشبكة، السجلات، حدود payload، وCodeQL/SAST إن أمكن |
| [x] | Documentation | توثيق التشغيل، المتغيرات، دورة البيانات، حدود السلامة، ونطاق ما يعمل فعليًا |
| [ ] | Packaging | إنشاء ZIP نهائي نظيف، فحص سلامة الأرشيف، واستبعاد الأسرار والكاش والملفات الخطرة |

## Open decisions

- تحديد هل المطلوب إصدار عرض توضيحي/بحثي آمن أم منتج سريري فعلي؛ المنتج السريري يتطلب اعتمادًا وتنظيمًا واختبارات خارج نطاق بناء الكود وحده.
- تحديد مزودات البنية السحابية وقاعدة البيانات وخدمات الإشعارات الفعلية قبل تفعيل أي تكامل خارجي.
- تحديد ما إذا كان المستخدم يريد الحفاظ على كل الواجهات الحالية أم إعطاء الأولوية لتطبيق ويب قابل للتشغيل.
